# Curiosity Builds 的制作经验

这是从 v1–v10 的代码、修订记录和最终交付中整理的项目经验。
引用的提示词和历史要求是资料，新的制作任务仍以当次用户要求为准。

## 一段只解释一个问题

最终从 Balanced Chess 直接开始，用 **What Can Curiosity Build?** 作第一段标题；
没有再加一个独立片头或重复切换标题。九段都用同一种节奏：
单独的大问题 → 同一个标题缩小、移到左侧，右侧出现概念图 →
标题消失，左侧换成制作提示、右侧保留过程画面 → 实际 Demo。

关键是“同一个标题连续移动”。把大标题淡出，再在新位置淡入另一个标题，
会失去这一关系；省略最开始的单独标题也不符合最后的修订。
v10 用一个标题节点，30–54 帧从 scale 1.38 缩到 1，同时移动位置。
标题在第 90 帧消失，制作文字从第 96 帧开始；两者不重叠。
每段介绍固定 216 帧（7.2 秒），最后没有再居中放大的第三种过程布局或底部步骤链。

证据：[最后修订](records/v10/revision-request.txt)、
[布局参数](records/v10/revision-design.json)、
[真实渲染的标题像素位置](records/v10/title-motion-pixels.json)。

## 概念图和真实项目各有用途

代码绘制的几何、ImageGen 草稿用来解释想法，随后用真实应用录像展示结果。
Van Gogh 和 Journey 最后采用“一半线稿、一半上色”的建筑概念图，
比程序占位图更能表达从想法到可探索空间的过程。
魔方也是未完成的设计稿，保持正确透视、直立、等比缩放和干净深蓝背景。
不要让制作示意看起来像另一款已经完成的产品。

修改画廊图时，提示词锁定原构图、透视、墙体和画作位置，只改完成程度。
两半共享连续几何，过渡处没有分割线。原图、第一次生成提示词、最后编辑提示词
分别有来源记录；只留下最后一句提示词不足以复原编辑过程。
本次保存这些文字和被省略图片的哈希，重新生成只能获得新的近似作品。

见 [v10 图像提示词](../../src/videos/curiosity-builds-v10/assets) 和
[封面制作链](covers)。

## 构图要保留项目真正需要看的部分

- **魔方**：最终用完整 1920×1080 网页，不裁掉右侧面板或顶部解法步骤。
  v5 的统一裁剪方案不适用于最终魔方画面；v7 的记录明确改成 `fps=30,setsar=1`。
- **Bible**：以完整的自然视窗录制，先在首页选择玩法，再实际完成 Sequence 和 Next Word。
  原始视窗为 1280×720，输出 1920×1080；“完整视窗”不等于禁止这一等比输出。
  播放画面约 2 倍速，音乐仍保留演奏原速。
- **Sweet Home 3D**：只显示下方真实 3D 模型，不把上面的二维平面或工具栏带进视频。
  使用用户选定的起始相机，不随意重置；最终裁剪为 x=260、y=560、1480×520。
  105 张原始帧分配给 120 个输出帧，画面率为 0.875，避免再开一个视频解码器。
- **过山车**：入口、俯瞰和乘坐画面保持原生 `spaceGlass` 冰蓝漏斗、白色黑洞外观，
  不能只靠后期滤镜假装已切换应用材质。原来的 Möbius 乘坐镜头保留 12 秒。

见 [cube-framing.json](records/v10/cube-framing.json)、
[Bible 检查](records/v10/bible-natural-verification.json)、
[模型裁剪](records/v10/house-model-crop.json)、
[原生材质记录](records/v10/ice-blue-native.json)。

## 连续运动需要连续录制

Sky 最后是一条 25 秒、750 帧的连续镜头：真实 transition room 飞行 → 进门 →
边绕行边上升 → 高度稳定后俯瞰绕行。前几版的分段镜头不能替代这个体验。
录制使用应用手动时钟，以 30 fps 逐帧截图送入 FFmpeg，跳过加载等待，
不在可见运动中加相机瞬移或剪切。

进入后的高度用 smoothstep 平滑上升，16 秒后停在地面以上 14.5；
相机仍沿水平方向绕行。通过逐帧记录的 phase、eye、target 和错误列表确认运动完成。
归档中的 Sky 脚本通过录制页路由加载 Cosmic Cliffs，本次不修改线上天空默认值。

见 [capture-sky.cjs](../../scripts/curiosity-builds-v10/capture-sky.cjs) 和
[相机轨迹记录](records/v10/sky-continuous.json)。

## 给真实录像留下真实性证据

Chess 有真实走子事件，COMEBACK 和 ROCKFALL 单独录规则演示。
Coder Arena 展示实际对战；Monthly Ranking 用的是历史八机器人服务器对战录像，
因此发布文案写清是 archived server battle，不把它当成当前月份的实时榜单。
应用名称后来改为 Balanced Chess，旧捕获提交和后续名称发布提交分别记录。

对“完整网页”“原生材质”“玩法成功”等要求，用截图、事件和帧数核对实际输出，
不能仅靠脚本注释或编码器退出码。以后若重录，旧证明只能解释原片，不能证明新片。

## 转场不能偷偷改变字幕时钟

直接用 concat demuxer 拼接 Remotion 和 FFmpeg 各自编码的片段，
可能因 time base 差异丢帧。早期脚本因此改成解码后统一帧率、PTS 和 time base。
最后的叠化又加了短暂的克隆边缘帧：在原剪切点两侧居中重叠，
保持每段原有帧数和字幕时钟。

最终参数：项目之间 24 帧、建造介绍到 Demo 18 帧、段内镜头 12 帧。
全片仍是 8514 帧；v9→v10 只改变标题动画，11 个 SRT 文件逐字节不变，音乐母带复用。
检查时同时看输入/输出帧数、章节起点和字幕末尾，不能只看格式标记的 duration。

见 [render.py](../../scripts/curiosity-builds-v10/render.py)、
[未变动时钟的记录](records/v10/unchanged-timing.json)。

## 编排音乐，而不是给每段铺同一条底音

从肖邦《雨滴》到德彪西《月光》、肖邦夜曲、巴赫《Air》，再进入莫扎特序曲，
音乐随项目从安静探索走向游戏和乘坐。莫扎特分成两段连续编排，最后接真正的管弦乐终曲。
只对各段做恒定增益和淡变，保留演奏速度与内部动态；画面加速不带动音乐加速。

换曲用 2 秒等功率交叉淡变；片头音乐淡入 1.2 秒，片尾淡出 2.4 秒。
独立分段还要另加边缘淡入淡出，否则从全片截下来的音乐可能突然开始或中断。
无配音的原片不需要套用旁白 ducking；以后若增加配音，重新按仓库规则混音。

保留具体录音版本而不只是作曲家和曲名；`music-sources.json`、音乐 cue 和
[交付署名](delivery/音乐来源与署名.txt) 一起保存。

## 封面的编辑也要有版本链

英文最终为 B 方案的 v6，中文封面基于同一张英文图修改文字。
保留画廊半线稿/半上色、虚化过山车背景和中性白标题的光影，修改时不要顺带重画构图。
中文标题是“从想法 / 到世界”，英文为 “From Ideas / to Worlds”；
这是本片当时选定的封面文字，与视频标题的问题句不同。

留存生成参考、初始提示词和每次修改提示词，才能知道修改的目标与已接受的部分。
最终上传文案从 `youtube.json` 读取，不从 `previous-*` 文件猜最后版本。

## 收尾时先提交源文件，再处理磁盘

工作文件在仓库目录中不等于已经进入 Git。此次源文件全是 untracked；
没有这个归档 PR，清掉电脑后远端仓库里仍找不到它们。

数据版本也不独立：v10 的 captures 和 edit 经多级软链接回到 v5、v6、v7、v8、v9，
音乐 WAV 直接指向 v5。保留一个 `v10` 目录不足以保留重建能力。
归档时把链接最终落点、文件哈希、私人原件和可重录部分一起列出。
新项目可以从一开始采用“代码 + 小型文字记录进 Git；媒体集中存放”的习惯，
减少逐版本复制整棵工程和继承过期校验数字的情况。
